# Drumr framework skills

Copilot skills are a collection of domain-specific implementation rules, patterns, and best practices for Drumr framework development. They are designed to guide developers in writing code that adheres to Drumr's architectural conventions and leverages its features effectively. It avoids generic coding advice and hallucinations, and focuses on Drumr-specific guidance, ensuring that generated code is maintainable, consistent, and aligned with the framework's design principles.

## How to use skills in GitHub Copilot Chat

Skills are added with `drumr create-app` and added/updated with `drumr setup` inside your app. They are automatically included in the context of GitHub Copilot Chat when working within a Drumr app repository. When you ask Copilot Chat to generate code, it will reference the relevant skills based on the type of code you're asking for. For example, if you ask for help implementing a new API endpoint, Copilot Chat will reference the **"Backend API"** skill to ensure that the generated code follows Drumr's conventions for API implementation.

You can also explicitly reference a skill in your prompt to ensure that Copilot Chat uses it as a guide for code generation.

> For example, you could say:
>
> - _"Using the Backend API skill, generate a new GraphQL query for fetching user data."_
> - _"`/backend-api` Generate a new GraphQL query for fetching user data."_
>
> This will signal to Copilot Chat that it should use the **"Backend API"** skill as a reference when generating the code.

---
Criticality reflects the **blast radius of a defect or gap in that skill**: how broadly incorrect guidance propagates into broken or insecure application code. Ratings are based on framework source structure (`core/backend/src/`, `core/frontend/src/`) and real usage in `apps/project-management-app`.

| --- | --- | --- |
| **Backend** |  |  |
| Actions | high | Actions are the sole entry point for every API request and UI operation. Incorrect patterns (wrong `canExecute` signature, missing permission registration, thrown instead of returned `ExpectedError`) silently break all endpoints. The project-management-app has 15+ actions across projects, tasks, and global scope — any systemic defect affects the entire API surface. |
| API | high | The `crud.api: 'gql'` configuration on `@DataModel` is the single switch that exposes entities to GraphQL. Wrong patterns (missing `crud` options, incorrect action exposure) make CRUD unavailable for all consuming views without an obvious error at design time. |
| Data Models | high | Data models define the schema for every entity, field, relationship, validation, and UI metadata. They are the foundation for persistence, GraphQL types, form rendering, and serialization. All 13 models in the project-management-app cascade defects to the API, database, and UI simultaneously. |
| Data Sources | high | The datasource is the prerequisite for all persistence. Incorrect configuration (`@DataSource`, TypeORM wiring, lifecycle hooks) prevents the app from connecting to the database entirely. All CRUD and query operations fail silently or at boot time. |
| Authentication & Permissions | high | Security defects are unconditionally high criticality. Missing or incorrect permission rules (`definePermissionsForRole`, CASL conditions) can expose records, allow unauthorized action execution, or lock legitimate users out. The project-management-app enforces role-based access across 5+ roles. |
| Tech Stack | medium | Acts as a troubleshooting and library-selection reference rather than a code-generation guide. Wrong guidance leads developers toward using raw TypeORM, Winston, or Apollo directly instead of framework abstractions — producing unmaintainable code — but does not break runtime immediately. |
| App bootstrap | high | The backend app bootstrap (@App() + BaseApp) is the single startup orchestration point for lifecycle hooks, config loading, service/datasource overrides, and runtime initialization. Incorrect guidance can prevent startup, misconfigure infrastructure wiring, or break app-wide behavior before any action executes. |
| Context | medium | Backend `Context` gives actions and services access to the current user, action metadata, and workflow state. Incorrect usage (wrong injection, unsafe stack utility calls) causes subtle bugs in user-scoped logic, bulk operation metadata, and context-aware permission checks — but only in code paths that read context. |
| Workflows | high | Workflows power long-running, durable business processes (report generation, task approval, bulk import, project archiving in the project-management-app). Wrong patterns (missing `@Step`, non-idempotent logic, skipped `callStep`) cause data loss or stuck executions in production. |
| Queues | low | Queues configure execution behavior for existing workflows (concurrency, retries, timeouts). A defect degrades throughput or retry behavior but does not break core business functionality. |
| Services | medium | Services provide shared, reusable backend logic injected into actions and workflows (e.g., `ActivityLogService`, `TaskPriorityEvaluator`, `EmailService`). Incorrect DI patterns or wrong scope choices cause silent singleton/request-scope bugs across multiple consumers. |
| Files | low | File handling is a specialized extension for apps that need upload/download (e.g., the `File` model attached to `Task`). A defect breaks file-specific flows only; core project and task management remains unaffected. Narrow scope limits blast radius. |
| Components | medium | UI component factories (`textInput`, `moneyLabel`, `choiceDropdown`, `referenceDropdown`, etc.) configured on backend field decorators drive all form and table rendering. Incorrect factory usage or missing `ui` bindings cause fields to render with the wrong control or no control at all — visible immediately in the UI but contained to field-level rendering. |
| Datasets | low | Datasets exist exclusively for seeding development and test environments (`drumr ds load`). A defect causes incorrect or missing fixture data, impacting test reliability and developer onboarding — but has zero impact on production runtime behavior. |
| **Frontend** |  |  |
| API | high | The frontend operation builder (`uiFindBy`, `uiCreate`, `dataFindById`, etc.) is the only way views consume backend data. Wrong query builder patterns, incorrect UI-vs-data operation selection, or broken field expansion break data fetching and mutation across all views. Every view in the project-management-app depends on this layer. |
| Tech Stack | medium | Establishes component selection priority (framework-first → Ant Design Pro → base Ant Design) and identifies Apollo Client as the data-fetching mechanism. Ignoring this guidance produces technically working but non-standard code that bypasses framework caching and field resolution — degrading maintainability and consistency rather than breaking features outright. |
| App Bootstrap | high | The frontend app bootstrap (`app.ts` + `configureApp(app)` + `app.runtime.ts`) is the single entry point for runtime exports, providers, registration order, and global app settings. Incorrect guidance (missing runtime exports, wrong provider wiring, or incomplete bootstrap composition) can prevent app startup or break initialization behavior across all frontend views. |
| Declarative model/action config | high | Frontend defaults control model field rendering, default CRUD view resolution, action button metadata, action param presentation, and functional action-view registration. Incorrect guidance propagates wrong labels, components, visibility rules, and navigation behavior across many screens at once. |
| Layouts | medium | The layout shell controls navigation mode, menus, header, and footer. An incorrect layout (broken menu wiring, wrong `Navigation` value) makes the entire app unnavigable. However, layouts are defined once per app, defects are immediately visible, and they do not affect data integrity. |
| Views (general) | high | The general views skill defines the toolbar DSL, header/footer configuration, UI API binding, route registration via `app.registerRoutes()`, and the component decision table shared by **all** view kinds. A defect here cascades into every table, form, action, and custom view. The 25+ views in the project-management-app all inherit these foundational concepts. |
| Form Views | high | `CreateView`, `EditView`, and `ReadView` are the most frequently implemented view types in any CRUD application. Incorrect prop patterns (`beforeSave`, `onSaved`), wrong field configuration, or broken refresh modes cause silent data loss or corrupted form state during the most common user interactions. |
| Table Views | high | `TableView` is the primary browsing surface for every data model. Incorrect column configuration, missing sort/pagination setup, or wrong toolbar wiring break the list experience for all records. Every data model in the project-management-app has a corresponding table view. |
| Action Views | medium | `ActionView` provides custom param forms for actions. A defect (missing `initialData`, wrong `ui.view` link to the backend action) breaks the action's form UI. However, the action itself can still execute via default param handling — the blast radius is limited to the custom UX layer. |
| Custom Views | medium | Custom views power free-form screens: `DashboardView`, `SummaryView`, `ActivityLogView` in the project-management-app. A defect (wrong lifecycle hooks) breaks specific custom pages without affecting core CRUD flows. |
| Notifications | medium | Notifications govern user feedback primitives (`getApp()`, `this.app`, message/modal/notification) used across views and non-view helpers. Incorrect guidance does not usually corrupt data, but it creates misleading UX (missing confirmations, silent failures, inconsistent success/error feedback) and can spread anti-patterns like direct `antd` message/modal usage across many files. |
| Services | medium | Frontend services centralize reusable client-side logic (GraphQL orchestration, caching, cross-view state). Incorrect DI patterns (wrong `@Inject`, broken singleton wiring) cause resolution errors that can cascade across all views consuming the broken service. |
| Helpers | medium | Navigation helpers (`openView`, `closeView`) and the toolbar DSL are used across nearly every view in the project-management-app. Incorrect usage (wrong container type, hallucinated APIs) causes broken navigation and non-functional action buttons — impactful but typically caught during development. |
| Components | high | `DataForm`, `DataTable`, and `DataField` are the core rendering components composed by every view. A defect (e.g., importing raw Ant Design instead of the framework wrapper, incorrect `DataField` prop wiring) bypasses the field resolution pipeline, breaking metadata-driven rendering for forms, tables, and field displays across the entire application. |
| Context | medium | The frontend `Context` singleton provides access to the authenticated user, navigation path, and mounted view state. Incorrect usage (`useContextValue` with unstable selectors, wrong `put()`/`notifyChange()` calls) causes excessive re-renders or stale state — but only in views that implement context-reactive logic. |
| **CLI** |  |  |
| Commands | medium | CLI commands drive the full developer workflow (scaffold, setup, run, build, sync-metadata, dataset loading). Wrong command syntax or missing flags cause broken project initialization, stale GraphQL schemas, or failed deployments — impacting every developer on the project but not affecting production runtime directly. |
| **Testing** |  |  |
| testing-unit | low | Unit tests validate individual services, actions, and helpers in isolation. A defect in this skill leads to poorly structured or unreliable unit tests, reducing confidence in isolated logic. The blast radius is contained: wrong unit tests do not cause production failures directly. |
| testing-integration | medium | Integration tests validate multi-layer interactions (action → service → datasource, view → mocked API). A defect produces tests that miss real integration bugs, allowing failures in action-to-service or form-to-API flows to reach production undetected — higher impact than unit test gaps. |
| testing-e2e | medium | E2E tests exercise full-stack flows through a real browser (Playwright + DrumrTestKit). A defect in this skill produces flaky or incomplete regression suites, allowing critical user-facing regressions (CRUD flows, navigation, permissions) to slip through. Broader coverage scope than integration tests amplifies the quality risk. |
